# masar_diwan ("مسار ديوان")

A custom Frappe app built on ERPNext v16 for registering, tracking, and archiving an organization's correspondence (incoming / outgoing / internal / circulars), with per-type reference numbering, QR/barcode tracking, department + confidentiality-tiered permissions, a full access audit log, a lightweight tracking portal for Website Users, a "diwan tray" draft/approval flow, and delivery-sheet / envelope / label printing.

Built entirely in this session by working through a 12-phase spec, phase by phase, each verified with real test data before moving on. **All 12 phases are complete.** Installed on site `bob.local` in this bench.

**Note on provenance**: a follow-up prompt once referenced a "previous cloud session" that had supposedly made further changes (workflow definitions, an access-log download route, a custom Workspace icon) via a patch file it couldn't push. No such patch file existed anywhere on this machine, and `git log`/`git ls-remote` showed no commits beyond this app's own history — there was no other session's work to recover. The workflows *did* already exist (from this app's own earlier phases) but had a real, separate bug: they'd never been exported to disk (see gotcha #6 below), which is probably what that prompt's premise was actually (if indirectly) pointing at. Recorded here so a future session doesn't go looking for a patch that was never real.

A later prompt pasted two `git am`-formatted patches directly (real, well-formed patch content this time, unlike the phantom one above). By that point almost everything in them had already been independently built and *live-verified* here — applying them wholesale would have conflicted with the working tree and, in a couple of spots, actively regressed already-fixed bugs (their download endpoint hardcoded `channel="Portal"`, exactly the bug already found and fixed; their Number Card for "Referred / In Progress" kept the literal `/` in its name, exactly the export-crashing bug already found and fixed in gotcha #7). Rather than `git am`-ing it, reviewed it as a diff against what already existed and cherry-picked the genuinely new, correct deltas: (1) `Access Log Entry`'s DocPerm for `Diwan Officer`/`Senior Management` had drifted to include `create`/`write`/`delete`/`share` despite the doctype's own "immutable audit log" design intent — tightened back to read/report/export/print only; (2) `_log_denial()` had a stale `# TODO (phase 6)` and was only writing a server log line, not an actual `Access Log Entry` row — fixed for real; (3) a sensible ownership condition on the Department Head's "Mark Completed" transition (`doc.current_owner == frappe.session.user`) that this app's own original Phase 3 build never had; (4) the "Reject" workflow action was missing its Arabic translation. All four confirmed as real, verified gaps and fixed directly in this repo's actual files, not by applying the pasted patch.

## Core design decisions

- **Everything is a customizable master, nothing is hardcoded.** Correspondence Type, Correspondence Category, and Department are all just Link fields to ordinary Frappe masters — the app makes no assumption about what types/categories a given organization uses.
- **One app, three front doors, one permission engine.** Website Users get a portal page at `/track` (search + QR/barcode scanning); System Users get the same functionality without leaving `/app` via the Desk Page "Correspondence Tracking" (`masar_diwan/masar_diwan/page/correspondence_track/`); System Users who prefer the standard list/form also just use `Correspondence` directly. All three call the exact same `masar_diwan.api.portal` functions, which in turn call `masar_diwan.permissions.has_permission()` / `get_user_departments()` — there is no separate, weaker "portal" permission model, and `channel` in the Access Log is inferred per-call from `User.user_type`, never hardcoded, so the same functions correctly log "Desk" or "Portal" depending on who's actually calling.
- **Diwan Tray separates drafting from registering.** Any role can submit a `Correspondence Request`; only a Diwan Officer's approval creates the officially numbered `Correspondence` record. This is deliberate — it's the "who starts the letter vs. who registers it" split the spec asked for.

## Permission model (read this before touching `Correspondence`)

Implemented in `masar_diwan/permissions.py`, wired via `hooks.py` (`has_permission` + `permission_query_conditions` for `Correspondence`). Two independent, stacked rules, both server-side, both reused by Desk and Portal:

1. **Department scoping** — a user sees a `Correspondence` only if it belongs to a department they're linked to via a `User Permission` (`allow="Department"`), *unless* their role is in `DEPARTMENT_EXEMPT_ROLES` (`Diwan Officer`, `Senior Management`). The `department` field has `"ignore_user_permissions": 1` set in its JSON specifically so Frappe's own automatic Link-field User Permission enforcement doesn't also kick in and double-restrict (or silently conflict with) this custom logic — if you ever add another department-like Link field to a doctype, remember this flag.
   Every denial from `has_permission()` goes through `_log_denial()`, which writes a real `Access Log Entry` (`event_type="View"`, `result="Denied"`) via `access_log.log_event()` — this closed out a TODO that had lingered since Phase 6 (it used to just write a server log line, not an actual audit row).
2. **Confidentiality tiering**, independent of department:
   - `Normal`: department rule only.
   - `Confidential`: `current_owner`, department members, `authorized_viewers`, `Diwan Officer`, `Senior Management`.
   - `Highly Confidential`: only `authorized_viewers` + `Senior Management` — even the assigned department's own head is excluded unless explicitly added to `authorized_viewers`.

**Deliberate deviation from spec 4.3**: restricted rows are *excluded* from Desk List/Report View (standard, secure Frappe behavior via `get_permission_query_conditions`), not shown as masked "•• مقيّد ••" placeholder rows. Implementing real per-row field-masking in Frappe's stock Desk list pipeline would need fragile, deep overrides of internal query/rendering code shared by every doctype on the bench. The literal masked-placeholder UX **is** implemented, faithfully, in the one place we fully control: `masar_diwan/api/portal.py::search_correspondence()` masks `subject`/`subject_en`/`party` on rows the user's confidentiality tier doesn't clear, while department-scoped rows are still hard-excluded there too.

## Reference numbering

`Correspondence.autoname()` (`masar_diwan/masar_diwan/doctype/correspondence/correspondence.py`) calls `masar_diwan/utils/numbering.py::get_next_reference_no()`, which does **not** use Naming Series — it atomically locks the matching row in `Correspondence Settings`'s `numbering_rules` child table (`SELECT ... FOR UPDATE`), auto-provisions a rule from the `Correspondence Type`'s own `prefix` if none exists yet, resets the counter when the calendar year changes (if `reset_yearly`), and builds `{prefix}-{year}-{padded_number}` (e.g. `و-2026-0001`).

`Delivery Sheet` and `Envelope`, by contrast, use Frappe's own built-in series mechanism (`"autoname": "format:كشف-{YYYY}-{###}"` / `"naming_rule": "Expression"`, backed by Frappe's `tabSeries` table) — they didn't need custom locking code because there's only one series each, not one-per-type.

## QR codes

Two separate mechanisms, used for different purposes — don't conflate them:
- `masar_diwan/utils/qrcode_utils.py::attach_tracking_qr_code(doc)` — generates a QR encoding the `/track?ref=...` URL, saves it as a **stored private File** attached to `Correspondence.qr_code` (an Attach Image field), called from `after_insert()`. This is the one reused by the `Document Label` print format.
- `masar_diwan/utils/qrcode_utils.py::qr_data_uri(text)` — renders a QR straight to a base64 `data:` URI with no stored File at all, registered as a Jinja global (`hooks.py` → `jinja.methods`) for use directly inside Print Format HTML (`{{ qr_data_uri(doc.delivery_sheet_no) }}`). Used by `Delivery Sheet Print` and `Envelope Label`.

## Access Log

Doctype is named **`Access Log Entry`**, not `Access Log` — that name collides with a built-in core Frappe doctype (data-export tracking). Everything funnels through `masar_diwan/access_log.py::log_event()`:
- Computes `is_new_ip` by checking prior `Access Log Entry` rows for that user+IP.
- Infers `channel` from `User.user_type` when not passed explicitly (`Website User` → `Portal`, else `Desk`).
- `on_session_creation` hook → logs `Login`.
- `log_view()` (whitelisted) explicitly re-checks `frappe.has_permission` and logs Success/Denied — called from `correspondence.js` on Desk form load, and from the portal search.
- `get_tracking_detail()` in `api/portal.py` logs `QR Scan` or `Barcode Scan` depending on the `via` param — same code path for both, since a camera scan and a barcode-reader keystroke both just resolve to `/track?ref=...`.
- `Correspondence Request` logs a `Tray Decision` whenever a Diwan Officer moves a request *out of* "Under Review" (approve/reject/needs-revision) — not on the requester's own "Submit".
- `masar_diwan.api.portal.download_attachment(file_id)` is the logged download path: re-checks `has_permission` on the *Correspondence* the file is attached to (not just File-level access), logs `Download` Success/Denied either way, then streams via the standard `frappe.local.response.filename` / `.filecontent` / `.type = "download"` pattern (same one `frappe.handler.download_file` itself uses). Still deliberately **not** wired into the raw `/private/files/...` static route — that route is shared by every app on this bench and patching it is out of scope — but every download that goes through the app's own UI (portal detail view, Desk "Correspondence Tracking" page) now goes through this endpoint instead of a raw file link.

Reporting: `Access Log Report` (Script Report, `masar_diwan/masar_diwan/report/access_log_report/`) has the 8 filters (user, event_type, channel, result, reference_doctype, is_new_ip, from_date, to_date) and 4 `report_summary` cards (total/success/denied/new-IP). CSV export is Frappe's native report toolbar — no custom export button exists or is needed.

## Workflows (3 total, all `workflow_state_field="status"` on an existing Select field, not a Link — no docstatus/submit involved, `doc_status` is `"0"` for every state)

- **Correspondence Workflow**: Draft → Under Review → Referred / In Progress → Completed → Archived (plus Under Review→Draft and Referred/In Progress→Under Review send-backs). `Correspondence.validate()` appends a `Correspondence Transfer Log` row on **any** status change via `get_doc_before_save()` comparison — this does not depend on Workflow Transition Action hooks, so a direct/manual status edit still gets logged. Both `Correspondence Employee` and `Department Head` can Submit for Review from Draft (this was originally Employee-only — an inconsistency with every other transition in this workflow already having matching role pairs, fixed later). The Department Head's "Mark Completed" transition additionally has `"condition": "doc.current_owner == frappe.session.user"` — a Department Head can only complete correspondence they're the current owner of; `Diwan Officer` has no such restriction (oversight role).
- **Correspondence Request Workflow**: Draft → Pending Review → Under Review → {Needs Revision | Rejected | Approved & Numbered}. The "Approve & Register" transition is where `correspondence_request.py::register_correspondence()` creates the real `Correspondence` doc, requires `correspondence_type` to already be set (enforced there, not just in workflow config), and sets `resulting_correspondence` back via `db_set`.
- **Delivery Sheet Workflow**: Pending Delivery → Delivered → Receipt Confirmed. `delivery_sheet.py::validate()` blocks the final transition in code (not just workflow config) unless `signed_sheet_image` is attached. `on_update()` backfills every item's `Correspondence.delivery_sheet` once confirmed.

`Envelope.on_update()` implements a similar backfill for `Correspondence.envelope`, including *clearing* it on any correspondence removed from `envelope_documents` — it's the one doctype here with bidirectional link cleanup, not just forward-fill.

## Frappe framework gotchas hit during this build (worth knowing before you extend this app)

1. **`frappe.utils.file_manager.save_file()` needs `df="<fieldname>"`.** Omit it and Frappe's own core `on_update` hook (`frappe.core.doctype.file.utils.attach_files_to_document`) will find no File with a matching `attached_to_field`, and silently insert a *second*, properly-linked File — leaving the first as an orphan. Traced via `bench execute` with a monkeypatched `db_insert` to find this; not documented anywhere obvious.
2. **Link field default `"user"` vs `"__user"`.** The Desk-resolvable magic default keyword is `"__user"`. Using the literal `"user"` stamps the literal string `"user"` into the field via `_set_defaults()` when a document is created via plain server-side `frappe.get_doc({...}).insert()` (not through the Desk new-doc flow), and `_validate_links()` — which runs *before* `before_insert()` in `Document.insert()` — then throws `LinkValidationError`.
3. **`Access Log Entry.reference_name` is a Dynamic Link.** Logging an event for a reference that turns out not to exist (e.g. a bogus scanned QR code) throws `LinkValidationError` unless the insert passes `ignore_links=True`. An audit log must never fail to record exactly the event that matters most ("denied: not found").
4. **Editing a *standard* doc's JSON on disk (Print Format, Report, Workflow, etc.) after it's already in the DB is not resynced by a plain `bench migrate`** the way DocType JSON is. Confirmed again directly with `Workflow`: adding a new `Workflow Transition` row to the JSON and running `bench migrate` produced zero errors but the DB still only had the old rows. Use `frappe.reload_doc(module, doctype_folder, doc_folder, force=True)` (e.g. `frappe.reload_doc("masar_diwan", "workflow", "correspondence_workflow", force=True)`) to force it — `bench migrate` succeeding silently does **not** mean your JSON edit actually took effect; always verify against the DB (or re-run the behavior you changed) after editing a standard doc's JSON by hand.
5. **`allow_edit` on a Workflow's `states` table is Desk-UI-only** (disables field editing client-side per state) — it is not a server-side permission boundary. Real write enforcement is still the doctype's own DocPerm rows plus each Workflow Transition's `allowed` role.
6. **Not every "standard, module-owned" doctype auto-exports to disk on save the same way.** `DocType`/`Report`/`Print Format`/`Page`/`Workspace` (when `public=1`) all call `export_to_files()` unconditionally from their own `on_update()`. **`Number Card` and `Dashboard Chart` only do it when `is_standard=1`** — a flag that is easy to forget since it's not `is_public`/`public` like everywhere else. **`Workflow`'s controller never calls `export_to_files()` at all**, ever, under any flag — a Workflow built via `frappe.get_doc({...}).insert()` (as this app's 3 workflows originally were) lives only in that site's DB forever unless you explicitly call `frappe.modules.export_file.export_to_files(record_list=[["Workflow", name]], record_module="Masar Diwan")` yourself. This was a real, silent gap in this app for a while: the 3 workflows, 5 Number Cards, and 2 Dashboard Charts existed only in `bob.local`'s database and were never part of the app's shippable source — a fresh `bench install-app masar_diwan` elsewhere would not have recreated them, and would likely have broken the Workspace (which references the Number Cards/Charts by name). Fixed by setting `is_standard=1` on the cards/charts and explicitly calling `export_to_files()` for the workflows; see "Known open items" below for the full story.
7. **A `Number Card`/any doctype named with a literal `/` in it (e.g. a status value like "Referred / In Progress" used as a card label) will crash `export_to_files()`** — the exporter treats `/` as a path separator when building the folder name, producing a path like `.../correspondence___referred_/_in_progress/...json` whose parent directory doesn't exist, and dies with `FileNotFoundError`. It also leaves a broken empty directory behind from the partial write. Avoid `/` (and other path-unsafe characters) in the `name`/`label` of anything that gets auto-exported — rephrase instead (e.g. "Referred or In Progress").
9. **A single Arabic-letter reference-number prefix (و/ص/د/ت) immediately followed by Latin digits visually reverses under RTL, and `unicode-bidi: isolate` does NOT fix it.** Every `Correspondence` reference number this app generates looks like `{prefix}-{year}-{number}` (e.g. `و-2026-0001`, see "Reference numbering" above) - one RTL-strong Arabic letter directly adjacent to LTR-strong Latin digits/hyphens. Unicode's own bidi algorithm rule **W2** ("search backward from each instance of a European number until the first strong type is found; if an AL is found, change the type of the European number to Arabic number") plus the general embedding-level logic means the browser's default bidi resolution, in an RTL context (`dir="rtl"` on an ancestor, or just an RTL-majority paragraph), visually re-orders the piece after the Arabic letter - `و-2026-0001` can render as `0001-2026-و`, with the year and sequence number swapped in front of the prefix. This is genuine, spec-defined Unicode behavior, not an app bug or a font issue. Two plausible-looking fixes were tried and **both failed** in an earlier design-verification pass: `direction: ltr` alone (the browser still applies bidi *reordering* around the element based on its neighbors/ancestors - `direction` controls the base paragraph direction, not whether reordering happens at all) and `unicode-bidi: isolate` (isolates the element's own internal ordering from its surroundings, but does not override rule W2's reordering *within* that isolated run itself, since the run still contains a mix of AL and EN characters). The fix that actually works combines `direction: ltr` with `unicode-bidi: bidi-override` (not `isolate`) - `bidi-override` forces every character in the element to render in the declared direction, overriding the Unicode bidi algorithm's own per-character resolution entirely, which `isolate` deliberately does not do:
	```css
	.ref-code {
		direction: ltr;
		unicode-bidi: bidi-override; /* NOT isolate - isolate does not stop rule W2's own internal reordering */
		display: inline-block;
		font-variant-numeric: tabular-nums;
	}
	```
	For an *editable* reference-input field the same override needs to be applied inline (a class alone can be overridden by the browser's own form-control bidi defaults in some engines), e.g. `<input dir="ltr" style="direction:ltr; unicode-bidi:bidi-override;" ...>`. Applied everywhere a `Correspondence`/`Correspondence Request`/`Delivery Sheet`/`Envelope` reference number is rendered or entered across the app (2026-09-21 visual-identity pass, see below): `.ref-code` is defined once in each of the two shared stylesheets (`masar_diwan/public/css/diwan-portal.css` for the `www/` portals, `masar_diwan/public/css/masar_diwan-desk.css` for Desk) and reused via `class="ref-code"`; the three Print Formats (`Document Label`, `Envelope Label`, `Delivery Sheet Print`) apply the same two declarations inline instead, since a print-view render can't be assumed to reliably pull in either app stylesheet. Full file list in the dated section below.
10. **`frappe.reload_doc(..., force=True)` on a `Workspace` document can delete its own exported JSON file.** `Workspace.on_update()` deletes the *previous* module/title's exported folder whenever `has_value_changed("title")` or `("module")` is true (normal cleanup for an actual rename/module-move) — but `reload_doc`'s save path doesn't seem to set up the `_doc_before_save` baseline correctly, so those checks can spuriously read as "changed" even when neither field was touched, deleting the workspace's own current file. Full story and the corrected fix (use `frappe.db.set_value` instead, never `reload_doc`, for a `Workspace`) is in the "Workspace icon" section below — this contradicts what gotcha #4 above recommends for other doctypes, which is still correct for those, just not for `Workspace`.

## Workspace icon — reverted to a standard icon after a reported full-Desk outage

**Current state: the Masar Diwan workspace uses the standard, built-in `"stock"` icon** (`Workspace.icon = "stock"`, the exact same icon the real `Stock` workspace uses — confirmed by reading that workspace's own DB record, not guessed, and confirmed the `icon-stock` symbol genuinely exists in `frappe/public/icons/timeless/icons.svg`). `hooks.py`'s `app_include_icons` line is commented out — **no custom SVG file is loaded for this app's icon at all right now.**

**What happened**: an earlier session built a custom `icon-diwan-tray` symbol in `masar_diwan/public/icons.svg` (single `<path fill-rule="evenodd">`, no `<mask>`/`<defs>`/`<title>`, `currentColor`-based) to match a reference image, wired via `app_include_icons`, and verified — via real HTTP fetches of `/app` and of `/assets/masar_diwan/icons.svg` directly — that the file served correctly (200, well-formed, correct content) and appeared correctly in the boot payload. A later report described this custom icon causing a **complete Desk outage across every module**, with a hypothesis that a `<mask>` element or similar structural SVG issue broke the shared icon sprite injection for the whole site.

**What was actually found when re-investigating, before touching anything**: the committed file at that time (`git log -1` = `ebcb3f7`, matching `upstream/version-16` exactly, no uncommitted diff) contained *only* the safe evenodd-path version — no `<mask>`, no `<defs>`, no `<title>`, nothing matching the failure hypothesis. A fresh, disposable-test-user HTTP login and full `/app` page fetch at the time of the report returned a complete, well-formed 200 response (281KB, ending in a proper `</html>`), and `/assets/masar_diwan/icons.svg` served correctly (200, 487 bytes, matching the known-good content). Reading Frappe's own `include_icons()` Jinja helper (`frappe/utils/jinja_globals.py`) confirmed icon sprites are injected via an **async client-side `fetch()` + `insertAdjacentHTML()`** call, not a server-side template include — meaning even a malformed SVG response there would surface as a browser-console error on that one `fetch().then()` chain, not a server-side rendering failure severe enough to blank the entire page across all modules. In short: **the specific outage mechanism described could not be reproduced or corroborated from the server side** with the file that was actually deployed at the time.

**Decision made regardless of that inconclusive finding**: switched to the standard `"stock"` icon anyway, because (a) the user's request to drop the custom-SVG approach entirely was explicit and unconditional, not contingent on root-causing the exact failure, and (b) a zero-custom-file, already-battle-tested-by-every-other-Stock-workspace icon is strictly simpler and lower-risk than maintaining a bespoke SVG pipeline for a single icon, regardless of whether that pipeline was ever actually the culprit. `masar_diwan/public/icons.svg` was **left in the repo, unused** (not deleted) as a reference in case a custom icon is revisited later with a proper rendering tool available to verify it first. If a custom icon is ever wanted again: get a real rendering environment (a headless browser or `rsvg-convert`/similar, properly installed with explicit approval since it needs system libraries) before wiring anything into `app_include_icons` again, not after.

Verified after the switch: DB confirms `Workspace.icon = "stock"` and `Workspace Sidebar.header_icon = "stock"` (see gotcha #10 below for why both had to be updated separately), `app_include_icons` no longer lists `masar_diwan/public/icons.svg` at all, and a fresh disposable-user HTTP fetch of `/app` returned a complete 200 page with "Masar Diwan" correctly present, no "diwan-tray" string anywhere in the response, and no reference to the removed SVG file at all.

**A second, more serious incident happened while fixing this**: the first attempt to sync the JSON edit into the DB used `frappe.reload_doc("masar_diwan", "workspace", "masar_diwan", force=True)` — the exact same fix recommended earlier in this file for gotcha #4. This time it **deleted the Workspace's own exported JSON file from disk** (`masar_diwan/masar_diwan/workspace/masar_diwan/masar_diwan.json` vanished, confirmed missing via `ls`, confirmed via `git status` showing it as deleted). Root cause, read directly from `frappe/desk/doctype/workspace/workspace.py::Workspace.on_update()`:
```python
if self.has_value_changed("title") or self.has_value_changed("module"):
    previous = self.get_doc_before_save()
    if previous and previous.get("module") and previous.get("title"):
        delete_folder(previous.get("module"), "Workspace", previous.get("title"))
```
This exists to clean up the *old* exported folder when a Workspace is renamed or moved to a different module. `frappe.reload_doc()`'s internal save path apparently doesn't set up the `_doc_before_save` baseline the normal Desk-save flow does, so `has_value_changed("title")`/`("module")` spuriously evaluated as changed even though neither field was touched — triggering `delete_folder()` on the workspace's own current folder. The file was restored with `git checkout HEAD -- <path>` (safe, since it was already committed) and the `icon` field was re-applied by editing the JSON directly plus a raw `UPDATE` on the DB row, deliberately avoiding `reload_doc`/`doc.save()` on the `Workspace` doctype entirely this time.
**Corrected guidance for gotcha #4: do not use `frappe.reload_doc(..., force=True)` on a `Workspace` document specifically** — for a Workspace, sync a JSON field edit into the DB with a direct `frappe.db.set_value("Workspace", name, fieldname, value)` (or raw SQL `UPDATE`) instead, which never runs `on_update()` and so can't trigger this deletion path. `reload_doc` is still fine for the other doctypes it was used for earlier in this file (Print Format, Report, Workflow) — none of those have an equivalent title/module-triggered folder-deletion hook.

**Also found while re-verifying**: `Workspace` and `Workspace Sidebar` are separate doctypes with their *own, independently-stored* icon fields — `Workspace.icon` (used for the home-grid tile) and `Workspace Sidebar.header_icon` (copied once at sidebar-creation time, used for the sidebar section header). Changing one does not change the other; both had to be updated to fully remove every trace of the old custom icon.

## Why the Workspace didn't show in the Desk home grid (root cause, corrected)

An earlier pass in this project checked whether the "Masar Diwan" Workspace showed up on Desk by calling `frappe.desk.desktop.get_workspaces()` directly (later re-verified even more thoroughly: as a real HTTP call, through a real login session, replicating exactly what the browser's own `frappe.xcall("frappe.desk.desktop.get_workspaces", ...)` does) — and it correctly returned "Masar Diwan" every time. That check was accurate but **answering the wrong question**. `get_workspaces()` (and the `pages` list in `frappe.boot`) is not what the Desk home grid renders from.

The actual, separate mechanism is the **`Workspace Sidebar`** doctype — genuinely a different doctype from `Workspace` (not a guess; confirmed by reading `frappe/desk/doctype/workspace_sidebar/workspace_sidebar.py` and `frappe/boot.py`). The home grid is built from `bootinfo.workspace_sidebar_item`, populated by `frappe.boot.get_sidebar_items()`, which reads `frappe.get_all("Workspace Sidebar", ...)` — a completely separate table from `Workspace`. Confirmed live: `select name from \`tabWorkspace Sidebar\`` on `bob.local` listed every stock ERPNext workspace (Accounts Setup, Assets, Buying, Organization, ...) but had **no row at all for "Masar Diwan"**, even though the `Workspace` record itself was (and always had been) perfectly valid — `public=1`, `is_hidden=0`, `for_user` empty.

Why the row never existed: Frappe only auto-creates `Workspace Sidebar` rows once, via `frappe.utils.install.auto_generate_icons_and_sidebar()` → `create_workspace_sidebar_for_workspaces()`, run during `bench install-app` (visible in the install log as the "Creating Workspace Sidebars" line — this app's own Phase 0 install log had exactly that line). At that point in this app's build, the "Masar Diwan" `Workspace` record **did not exist yet** — it was created programmatically much later, in Phase 11, well after `install-app` had already run and generated sidebars for every workspace that existed at that moment. Nothing ever re-ran the generator afterward, so the newly-created Workspace silently never got a matching sidebar row. ## 2026-09-16: why `icon="stock"` never showed as an actual icon on the grid (final, root-caused)

The user personally logged into the real Desk with a real browser control tool and confirmed via a real, zoomed-in, side-by-side screenshot against the real `Stock` tile: "Masar Diwan" was showing a plain grey circle with the letter "M" — the generic initials fallback avatar — not the Stock icon, on two different accounts (Administrator and a persistent test account). Every previous session's "verified" claim about this icon had only ever checked `bootinfo`/database fields, never an actual rendered page — a repeat of the exact mistake standing rule #3 already existed to prevent. That rule is now rule #6 below, worded more forcefully, because it was violated twice in this same file.

**Root cause, found by reading the actual rendering code (`frappe/public/js/frappe/ui/desktop_icon.html` + `frappe/public/js/frappe/utils/utils.js`), not by guessing:**

The app-switcher grid tile **does not use the `Desktop Icon.icon` field at all**. Its image comes from `get_desktop_icon(label, variant)`, which:
1. Looks up the Desktop Icon record's **`app`** field.
2. If set, checks whether a physical file exists at `<app>/public/icons/desktop_icons/{light|dark}/<scrub(label)>.svg` — a real per-app artwork file, not a symbol-sprite reference (a completely different mechanism from `app_include_icons`/`icon-<name>` symbols, which *are* real and *do* get used, just not here).
3. If `app` is falsy, or no such file exists, it falls through past the `logo_url`/`icon_image`/Folder checks straight to `frappe.utils.desktop_icon(label, bg_color)` — which takes `label.charAt(0).toUpperCase()` and renders it in a circle colored from `desktop_pallete[bg_color]` (`gray` → `#7B808A`). This is *exactly* the grey "M" the user saw.

Why `app` was empty on our record: Frappe's own core `create_desktop_icons_from_workspace()` (the function `ensure_desktop_icon()` calls) has a genuine bug — it does `icon.app_name = app_name`, but the actual field on the `Desktop Icon` doctype is named `app`, not `app_name`. That assignment silently no-ops, so `app` is never populated for any workspace-derived Desktop Icon created this way (not specific to this app - this would happen for *any* app's workspace-derived Desktop Icon in this Frappe version). Setting `icon="stock"` on `Workspace`/`Workspace Sidebar`/`Desktop Icon` (all confirmed correct and consistent in the database, all real, all still true) was simply never going to change this tile's rendering, because that specific field isn't read by this specific code path at all.

**Decision, made by the user, not assumed**: keep the fallback avatar (grey circle, "M") as-is. Getting an actual icon image on this specific grid would require shipping a real `.svg` artwork file per app — which is still "a custom icon asset" in substance, the same category of thing the user asked to drop entirely in an earlier session. The fallback avatar is Frappe's normal, standard, expected appearance for any third-party app that hasn't shipped that file — not a defect in this app's code. **No further code change was made as a result of this investigation** (the earlier icon-field values are all still correct and harmless, just inert for this one specific view).

### Reported as vulnerabilities, empirically disproven (not false alarms to dismiss lightly — actually tested, not just re-argued)

5. **Reported: stored XSS via `Correspondence Request.draft_text` rendered with `| safe` in `www/diwan/queue/index.html` and `requests/index.html`.** `draft_text` is a `Text Editor` field with no `ignore_xss_filter` flag set, and Frappe core's `Document._validate()` unconditionally calls `_sanitize_content()` → `sanitize_html(value, linkify=True)` (`nh3`-based) on **every** save of every non-exempt field — including via `doc.insert(ignore_permissions=True)` (what `register_correspondence()` uses) and `frappe.client.insert`/`set_value` (what the portal pages use), not just Desk form saves. Proved this directly rather than trusting the source reading alone: inserted a `Correspondence Request` with `draft_text = '<script>alert(1)</script><img src=x onerror="alert(2)"><p onclick="evil()">hi</p>'` via `doc.insert(ignore_permissions=True)` and read back the stored value — `<script>`, `onerror`, and `onclick` were all gone; only `<img src="x"><p>hi</p>` survived. The `| safe` filter in the template is therefore rendering already-server-sanitized HTML (the correct pattern for displaying rich-text content, same idea as how Frappe's own Text Editor fields are meant to be shown elsewhere) — not an open injection point. No code change made.
6. **Reported: `</script>` breakout via `detail_json | safe` embedded in a raw `<script>` block in the same two pages** (`context.detail_json = frappe.as_json(context.detail)`, which does not escape `</`). Same underlying defense applies: `subject`/`decision_note`/`note_to_registrar`/`party_or_department` are all `Data`/`Small Text` fields with no `options == "Email"` exemption, so they go through the identical `_sanitize_content()` pipeline on save. Proved directly: saved `subject = 'Normal subject </script><script>alert(document.cookie)</script>'`, read back `"Normal subject "` — the entire script fragment was stripped before it ever reached the database, so it can't reach `frappe.as_json()`/the page at all. No code change made.

Neither of these two would still be false positives if a future field on either doctype is ever given `"ignore_xss_filter": 1` or changed to a fieldtype that skips `_sanitize_content()` (e.g. `Code`) — worth remembering if either doctype's fields change, but as of this audit, both are genuinely protected by Frappe core, not by anything in this app's own code.

### Document Access Profile + Confidentiality Level - the generalized engine

Two new master doctypes replace what used to be logic hardcoded around `Correspondence` specifically:

- **`Document Access Profile`** (one record per registered doctype, e.g. `Correspondence`): `department_field`, `owner_field` (defaults to the standard `owner` meta field - overridden to `current_owner` for `Correspondence`, which has always tracked ownership under its own fieldname, not the generic one), `status_field`, `reference_field`, `department_exempt_roles` (child table), `supports_confidentiality` + `confidentiality_field` + `authorized_viewer_doctype`, and `numbering_prefix_source_doctype`/`numbering_prefix_source_field` + `searchable_fields` (both reserved for Stage 2+ - the numbering engine and unified search haven't been wired to read them yet, see below).
- **`Confidentiality Level`** (any number of records, not fixed at three): `level_name`/`level_name_en`, `rank` (ordering only), and three independent per-level rules - `bypass_roles` (child table: roles that read a document at this level from any department regardless of ownership), `owner_can_read` (Check), `department_members_can_read` (Check).

**Deliberate deviation from the request's literal field list, made and documented rather than silently substituted**: the request specified `confidential_bypass_roles`/`highly_confidential_bypass_roles` as two named fields directly on `Document Access Profile`. That shape only works for exactly three fixed tiers - it can't express "two levels" or "four levels," which the same request explicitly asked `Confidentiality Level` to support as a genuinely dynamic master. Moved bypass-role configuration onto `Confidentiality Level` itself (one `bypass_roles` child table per level record) instead, which generalizes correctly to any number of levels without special-casing "the confidential one" and "the highly-confidential one" by name anywhere in code. `Document Access Profile` keeps only `department_exempt_roles`, which is genuinely per-doctype-type (not per-level).

`Correspondence` is registered with `department_field=department`, `owner_field=current_owner`, `department_exempt_roles=[Diwan Officer, Senior Management, System Manager]`, `confidentiality_field=confidentiality`, `authorized_viewer_doctype=Correspondence Authorized Viewer`. Three `Confidentiality Level` records were seeded to reproduce the original hardcoded three tiers *exactly*: `Normal` (rank 0, department_members_can_read=1, owner_can_read=1, no bypass roles - department scoping alone already covered everyone who needs access), `Confidential` (rank 1, department_members_can_read=1, owner_can_read=1, bypass_roles=[Diwan Officer, Senior Management, System Manager]), `Highly Confidential` (rank 2, department_members_can_read=**0**, owner_can_read=**0**, bypass_roles=[Senior Management]). The last one's `owner_can_read=0` deliberately preserves a real asymmetry found in the *original* code while re-deriving it line by line for this rewrite: `Confidential` explicitly checked `doc.current_owner == user`, but `Highly Confidential` never did - meaning a Highly Confidential document's own creator has never been able to read it back unless they also happened to be an authorized viewer or hold a bypass role. Whether that was ever intentional isn't clear from any prior session's notes; it wasn't invented by this rewrite, and wasn't silently "fixed" either - reproduced faithfully so behavior stayed byte-for-byte the same, flagged here for whoever owns this app's access policy to decide whether it's actually wanted.

`Correspondence.confidentiality` and `Correspondence Request.suggested_confidentiality` were both converted from a hardcoded `Select` (`Normal\nConfidential\nHighly Confidential`) to a `Link` -> `Confidentiality Level`. Confirmed this is safe at the data level before doing it: values are stored as plain strings in the DB either way, and the three `Confidentiality Level` records are named exactly matching the old Select options, so no existing row's stored value needed to change. **Known limitation, not fixed this pass**: two hand-built UI pickers - the confidentiality pill buttons in `correspondence_request_new.js` and the confidentiality radio buttons in `www/diwan/submit/index.html` - still hardcode the three level names/colors/labels rather than enumerating `Confidentiality Level` records dynamically. The underlying *engine* is now genuinely N-level-capable; these two pieces of hand-built UI are not, yet. A client configured with a different level count would need these two spots updated (or rebuilt to render dynamically) before the UI would reflect it - the permission logic itself would already be correct regardless.

### `permissions.py` rewrite - verified against a golden snapshot, not just re-read

`has_permission`/`get_permission_query_conditions` (the two Correspondence-specific entry points `hooks.py` must still register by name - Frappe requires an explicit per-doctype registration, which the request itself acknowledged can't be generalized away) are now thin wrappers over two new fully generic functions, `generic_has_permission(document_type, doc, ptype, user)` and `generic_get_permission_query_conditions(document_type, user)`, that read everything from `Document Access Profile`/`Confidentiality Level` instead of any hardcoded doctype/role/field name. `has_permission_correspondence_request`/`get_permission_query_conditions_correspondence_request` were deliberately left as their own small, un-generalized functions - `Correspondence Request` has no confidentiality tiering at all, and forcing a confidentiality-less doctype through the same profile shape for a department-only rule felt like premature abstraction for a rule this simple; they now read `department_exempt_roles` from the `Correspondence` profile via the new `get_department_exempt_roles()` accessor rather than a duplicated hardcoded role set, so there's still exactly one source of truth for that role list.

**Verification method**: before touching the file, ran a snapshot script across all 5 role-distinct persistent test users x all 7 live `Correspondence` records, capturing both `frappe.has_permission(..., "read")` *and* the actual `frappe.get_list(..., ignore_permissions=False)` visible-list result for each - 35 data points, both permission layers. (Caught and fixed a flaw in the snapshot script itself before trusting it: `frappe.get_all(..., ignore_permissions=False)` silently ignores that kwarg - `get_all`'s own source hardcodes `ignore_permissions=True` unconditionally - so the first snapshot attempt was measuring nothing. Switched to `frappe.get_list`, which honors it correctly, confirmed by first re-checking that `has_permission` and the visible list agreed with each other, which they did once measured correctly.) Re-ran the identical snapshot after the rewrite and diffed programmatically - one difference, in one user/document pair, correctly explained rather than dismissed (see below). Additionally re-verified live over real HTTP (`/track`, `/diwan/queue`, `/diwan/tray`, `/diwan/delivery_sheets`, `/diwan/envelopes`, `/diwan/audit_log`, `/diwan/submit`, `/diwan/requests`, plus the three Desk pages/forms) and with fresh disposable-user probes for System Manager bypass and cross-department create.

**A real, pre-existing bug was found via that diff, not introduced by it - and the fix was kept rather than reverted for exact fidelity.** `test.employee1@masar-diwan.local` (HR department) is an explicit `Correspondence Authorized Viewer` on `OU-2026-0002` (Finance department, Highly Confidential) - `has_permission` correctly said `True` for them on that document *both before and after* the rewrite. But the *original* `get_permission_query_conditions` excluded that row from their list view anyway, because its SQL combined the department clause with every confidentiality clause via a single top-level `AND` - an authorized viewer outside the document's own department satisfied the confidentiality clause but still failed the unrelated department clause, so the row was hidden from the list even though opening it directly by name has always worked. This directly violates this file's own long-standing documented invariant ("Both `has_permission`... and `get_permission_query_conditions`... must agree, so the list never shows a row the form would then refuse to open") - except backwards: the list was *hiding* a row the form *would* show, not the dangerous direction, but still a real inconsistency, confirmed by direct SQL inspection of `OU-2026-0002`'s department vs. `test.employee1`'s own `User Permission` department vs. the `Correspondence Authorized Viewer` row. The new engine builds each confidentiality level's visibility clause independently (bypass-roles OR owner OR authorized-viewer OR department-fallback, evaluated *per level*, not one department clause ANDed across everything), which happens to close this gap as a natural consequence of the more careful construction, not a deliberate extra fix. Kept the corrected behavior rather than deliberately reproducing the old inconsistency, since the corrected version is what this file's own documented design intent already says should happen.

## 2026-09-22: the real, central ERPNext dependency - `Department` itself - found, fixed, and proven live on a genuine Frappe-only site (`diwan.local`)

The previous session's ERPNext-independence audit found and removed two unused, decorative fields (`company`/`branch`) and declared the independence question blocked on getting a real Frappe-only site to test against. **The real finding**: `Department` - the doctype `Correspondence.department`, `Correspondence Request.department`, and `Correspondence Transfer Log.to_department` all Link to, and the entire department-scoping rule (rule 1 of this app's whole permission model, the one `Document Access Profile.department_field` is built around) depends on - is itself an ERPNext doctype (`erpnext/setup/doctype/department`), not core Frappe and not part of `hrms` either. Confirmed conclusively once a genuine ERPNext-free site (`diwan.local`, see below) became available: no `DocType` record, no `tabDepartment` table, and directly attempting to create one throws `ImportError: No module named 'frappe.core.doctype.department'`. `bench migrate` succeeding cleanly on that site earlier (previous session) was misleading - Frappe's Link-target validation doesn't re-check already-synced field definitions on a routine migrate, so the JSON sync goes through fine; the break only surfaces the moment anyone actually *uses* the field, confirmed by a real Error Log entry from someone's own earlier browser session on that site hitting exactly this (`frappe.desk.search.search_link` on `Correspondence Request`'s department field: `DocType Department not found`).

### The fix - `masar_diwan`-owned `Department`, same name, ERPNext-conditional, fully self-healing

`masar_diwan/install.py` gained four new pieces, all idempotent, all wrapped in try/except (never breaks a migrate), following this file's own established self-healing pattern (`ensure_workspace_sidebar()`/`ensure_desktop_icon()`):

- **`ensure_department_doctype()`** (`after_install` + `after_migrate`): if ERPNext is installed, or something already named "Department" exists, no-op immediately. Otherwise creates masar_diwan's own **`Department`** - same literal name, so the three Link fields above never need editing either way - as a `custom=1` DocType, built entirely at runtime via `frappe.get_doc({...}).insert()`, not as a static exported JSON file under this app's own `doctype/` folder (which would risk colliding with ERPNext's real `Department` on any site that *does* have ERPNext - a `custom=1` doctype needs no physical controller file at all, confirmed directly from `frappe.model.base_document.import_controller()`: "For `custom` type, return `frappe.model.document.Document`"). Fields: `department_name` (unique, required) and a plain self-`Link` `parent_department` - deliberately *not* a full NestedSet tree (`is_tree=1`); nothing in this app ever traverses department hierarchy, so the `lft`/`rgt` bookkeeping a real tree doctype needs isn't earning its complexity here. No `company` field or concept at all, since `Company` is equally ERPNext-only.

- **`rename_masar_department_before_erpnext_sync()`** (new `before_migrate` hook - this app's first one): if ERPNext is installed *and* the current "Department" doctype's own `module` is still "Masar Diwan" (i.e., ours, not ERPNext's), renames it to **`Masar Diwan Legacy Department`** via the standard `frappe.rename_doc("DocType", ...)`. Must run in `before_migrate`, confirmed by reading `frappe/migrate.py` directly: `pre_schema_updates()` (which runs `before_migrate` hooks, across *every* installed app) executes before `run_schema_updates()` (`frappe.model.sync.sync_all()`, which is what would create ERPNext's real `Department` for the first time) - waiting until `after_migrate` would let ERPNext's own sync collide with ours still sitting under the same name, within the same migrate run. No-ops in a single check on any site where ERPNext already owns `Department` (its `module` is "Setup", never "Masar Diwan") - **verified this literally never touches anything on `bob.local`**, not just reasoned about: ran `bench --site bob.local migrate` after all of this landed, zero errors, `Department.module` still `"Setup"`, no `Masar Diwan Legacy Department` ever created there.

- **`migrate_legacy_department_to_erpnext()`** (`after_migrate`): once ERPNext's real `Department` exists (checked via `module == "Setup"`) and at least one `Company` exists (else defers - logs why, retries automatically every future migrate, no manual intervention needed), matches each `Masar Diwan Legacy Department` row to a real ERPNext `Department` by `department_name` alone. Exactly one match -> migrates every real reference (`Correspondence.department`, `Correspondence Request.department`, `Correspondence Transfer Log.to_department`, and any `User Permission` row with `allow="Department"`) from the old name to the new one, via `frappe.db.set_value`/`frappe.db.sql`, not raw SQL guesswork against unknown schemas - these are the exact three fields already known and named in `DEPARTMENT_LINK_FIELDS`. Zero or multiple matches (ambiguous - could happen with more than one Company) -> **deliberately left unmigrated**, logged to Error Log with the specific reason, no silent guessing. A full JSON backup of every legacy row (name + department_name) is written to `sites/<site>/private/backups/masar_diwan/` before any deletion, every time there's something to migrate - a durable audit trail independent of whatever ends up in the DB afterward.

- **Cleanup, only once fully safe**: a legacy row is deleted only once *zero* real references to it remain anywhere (checked explicitly, not assumed) - an ambiguous/unmigrated row with live references is left completely alone, row and all. Only once every legacy row is gone does the whole `Masar Diwan Legacy Department` doctype get dropped, and only then are the three real Link fields' `options` explicitly reset back to plain `"Department"`.

**A genuinely subtle side effect was caught by reading Frappe's rename internals before writing any of this, not discovered by trial and error**: `frappe.rename_doc("DocType", "Department", "Masar Diwan Legacy Department")` internally calls `rename_doctype()` -> `update_options_for_fieldtype("Link", old, new)` (confirmed by reading `frappe/model/rename_doc.py` directly), which correctly bulk-updates every `DocField.options` pointing at the old name - but, on a `developer_mode=1` site (true of both `bob.local` and `diwan.local`), that same function *also* calls `.save()` on every affected DocType, which - since `Correspondence`/etc. are ordinary (non-custom) doctypes - re-exports their JSON straight to this app's own tracked source files on disk, momentarily writing `"options": "Masar Diwan Legacy Department"` into `correspondence.json` etc. as an unwanted side effect of what should be a purely transient, site-local migration step. Fixed by never trusting whatever the file happens to say afterward: `_restore_department_field_options()` explicitly sets each field's `options` back to `"Department"` through the ORM (`frappe.get_doc("DocType", ...); f.options = "Department"; doc.save()`) once cleanup is complete - a real `.save()`, not `frappe.reload_doc()` (which would just re-import whatever the possibly-still-wrong file already says), correcting both the live DocField row *and* re-exporting the JSON with the corrected value in the same step.

## 2026-09-22: Internal Mail Movement (closing the "internal mail between departments" requirements gap) + Document Access Profile generalized to multiple department fields

The original requirements letter's mail-management section asked for tracking internal envelope movement between departments (from/to, sender, content description, receipt confirmation with who/when) - genuinely different from `Correspondence Transfer Log`, which only records status changes on an already-registered `Correspondence` within one workflow, never a standalone from-department/to-department handoff that doesn't need a registered Correspondence at all. Closed this gap, and generalized the permission engine to support it properly rather than bolting on one-off logic - committed as `1171f40` (see `179dcd2`/`758848c`/`fb4c078` for everything before it, and this file's own entries dated 2026-09-21/22 above for the fuller history).

### `Document Access Profile.department_field` (single) -> `department_fields` (child table, OR)

A new `Internal Mail Movement` needs *two* department Link fields (`from_department`/`to_department`), not one - the existing single `department_field` Data field couldn't express that. Replaced with `department_fields`, a `Document Access Profile Department Field` child table (one `fieldname` row each); a document matches if the user belongs to *any* of the listed fields' department (logical OR), or holds an exempt role. `generic_has_permission()`/`generic_get_permission_query_conditions()` in `permissions.py` were rewritten to iterate the list instead of checking one field - the multi-field SQL clause is built the same way the original single-field one was, just OR'd across fields, with the "all configured fields empty -> unrestricted" fallback preserved exactly (reduces to the original single-field clause byte-for-byte when there's only one field).

**Migrated via a real patch** (`patches/migrate_department_field_to_department_fields.py`, `post_model_sync`), not a manual one-off script - this needs to run identically on any site, not just the two currently in hand. Reads the old `department_field` column via raw SQL (works even after it's no longer declared in the DocType JSON, since Frappe's schema sync never drops orphaned columns - confirmed multiple times already in this file) and appends a matching `department_fields` row for any non-empty value found.

**A real, non-obvious gotcha was hit and is worth remembering for any future Document Access Profile schema change**: after running the patch the first time, the newly-migrated `department_fields` data (and the underlying `department_field` value) came back **empty** on the very next inspection - not a patch bug. Root cause: `Document Access Profile` is a whole-doctype fixture (`hooks.py`'s `fixtures` list), and the *exported fixture JSON on disk* still had the old shape (`"department_field": "department"`, no `department_fields` table) at that point, since it hadn't been re-exported yet after the schema change. `sync_fixtures()` runs *after* `post_model_sync` patches in the very same `bench migrate` - so it silently re-imported the stale fixture right on top of the patch's freshly-migrated data, and since the fixture's `department_field` key no longer maps to any real field in the (already-changed) meta, that value was simply dropped on write, leaving both the old column and the new table empty. Fixed by re-exporting the fixture immediately (`bench export-fixtures --app masar_diwan`) and re-migrating to confirm stability before moving on. **Standing rule for next time**: any schema change to a fixture-exported doctype must be followed by re-exporting that fixture in the same pass, before the next migrate - never assume the old export is harmless just because it's "just a fixture."

**Golden snapshot, mandatory, run correctly this time (not against already-edited code)**: capturing a true "before" snapshot after `permissions.py` had already been edited would have been meaningless (the running code no longer matched the old schema) - `git stash`'d all the department_fields changes first, captured the real baseline (`has_permission` + actual `get_list` results, 5 test accounts x 7 `Correspondence` records = 35 points) against the genuinely original code+schema, then `git stash pop`'d, migrated, and re-captured. **Result: zero difference.** Confirms the generalization is fully transparent for `Correspondence`'s existing single-field profile.

### `Internal Mail Movement` - new doctype + 3-state Workflow

Fields: `from_department`/`to_department` (Link -> Department, both `ignore_user_permissions=1` matching the same convention already used on `Correspondence.department`), `sender_name` (Data, defaults to the creator's full name but editable - the actual sender may not be the System User recording it), `content_description` (Small Text), `related_correspondence` (Link -> Correspondence, optional, no enforcement either way), `status`/`sent_on`/`received_by`/`received_on`. ## 2026-09-24: per-category dynamic-field engine (Correspondence Category's own dynamic_fields), built from a detailed external brief

- No separate "bidirectional envelope/document search" API — the Link fields in both directions (`Envelope.envelope_documents` forward, `Correspondence.envelope` backward) are the whole mechanism; that's standard Frappe Link navigation, not a gap.

## How to verify this still works

There is no committed automated test suite for the custom business logic (numbering, permissions, workflows) beyond the standard Frappe-generated `test_*.py` stubs per doctype. Verification during this build was done with disposable scripts under a temporary `masar_diwan/setup/` package (created, exercised via `bench --site bob.local execute masar_diwan.setup.<script>.run`, then deleted — nothing under `setup/` is meant to persist in the repo). If you're validating a change, the fastest path is the same pattern: write a throwaway script that creates a `Correspondence Type`/`Correspondence Category`, drives a document through the relevant workflow with `frappe.model.workflow.apply_workflow`, and asserts on the result — then delete the script and run `bench --site bob.local migrate` to confirm nothing regressed structurally.

Full-app regression check: create a `Correspondence Request`, submit → review → approve (with `correspondence_type` set) to get a numbered `Correspondence`, run it through its own workflow to `Completed`, put it on a `Delivery Sheet` through to `Receipt Confirmed`, put it in an `Envelope`, and confirm it's both findable and correctly masked/excluded via `masar_diwan.api.portal.search_correspondence()` as a department-matched vs. department-mismatched Portal user. This exact sequence is what was last run clean, end to end, with no errors.

## Standing rules for whoever works on this repo next

1. **Keep this file current in the same session, not "later."** Whenever a bug is found and fixed, a phase advances, or a real gotcha is discovered, update the relevant section here before moving on.
2. **Give a full summary in the direct chat reply at the end of every session**, not only in this file — what was found broken, what was fixed and how it was verified, what still needs checking, what remains open. This file is the durable copy; the chat reply is what the user actually reads first.
3. **For anything about how something *visually renders* (an icon, a color, a layout, a fallback vs. the real thing) — checking `bootinfo`/the database/an API response is never sufficient proof, no matter how directly it seems to relate.** The only acceptable evidence is an actual screenshot of a page actually rendered in an actual browser. This was violated **twice** in this exact file on the icon question alone: first, multiple sessions reported the Workspace/Desktop Icon `icon` field as "verified" from database and boot-payload checks, when the field turned out to not even be read by the code path that renders that specific tile at all (see the section above) — the data was correct and the conclusion was still wrong. If this environment has no browser-automation tool available (check first — `chromium`/`chrome` binary, Playwright, Selenium, Puppeteer; as of this writing, none exist here), **say so explicitly and ask the user to confirm visually themselves** rather than reporting something as "verified." A data-layer check can rule out data-layer bugs; it can never on its own prove what a rendered pixel looks like. (Separately: a real HTTP fetch of the full page *is* legitimate evidence for "does the right data reach the browser," e.g. confirming `frappe.desk.desktop.get_workspaces()` isn't what renders the home grid at all — that's verifying data delivery, not visual rendering; don't conflate the two.)
4. **Any diagnostic action that changes real, shared, hard-to-reverse state — resetting a password, clicking a destructive UI action, running a command whose effect can't be inspected before it runs — must be flagged to the user immediately when it happens, or avoided entirely in favor of a disposable/reversible alternative (a throwaway test user, a copy, a dry run).** Not after the user notices it themselves. This happened once in this project: `bench set-password Administrator ...` was run to test a login-based theory instead of using a disposable test user (the pattern used successfully in every other verification here) — overwriting a real, unrecoverable credential on a real bench without asking first. Flagged immediately once noticed, but it should never have happened; the disposable-test-user pattern already established throughout this file's own verification sections was right there to reuse.
5. **A fix this file recommends for one situation is not automatically safe for a superficially similar one — re-check, don't just reuse.** Gotcha #4 recommends `frappe.reload_doc(..., force=True)` to force a standard doc's JSON edit into the DB. Reusing that exact recommendation on a `Workspace` document (gotcha #10) deleted the file it was meant to fix, because `Workspace` has its own `on_update()` deletion logic that Print Format/Report/Workflow don't have. Before applying a previously-documented fix to a new situation, check whether the target doctype has any doctype-specific hooks that could behave differently — grep the controller (`frappe/**/doctype/<name>/<name>.py`) for `on_update`/`before_save`/`on_trash` first, rather than assuming "this worked for doctype X, so it'll work the same way for doctype Y."
